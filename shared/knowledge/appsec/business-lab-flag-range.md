# 业务逻辑靶场（Flag制）实战打法 — 好靶场赛事22全系列沉淀

> 来源：好靶场(haobachang)赛事22支付逻辑方向 18 靶场实战（2026-11-16）。全部手法经实战验证。
> 适用：任何 Flag 制业务逻辑靶场（优惠卷/钱包/交易所/会员订阅类）。与 [[logic-test]] 互补：本篇是靶场化战法与具体 bypass 原语，logic-test 是方法论。

## 0. 平台交互范式（先于一切）

- OpenAPI 模式：`GET /api/openapi.json` 读接口规范 + `Agent-Token` 头认证（个人中心领取）。
  接口通常只有 4 个：`see_bug_list` / `see_bug_one` / `start_challenge` / `submit`。
- **实例寿命极短（30~90s）**：explore 可慢，**exploit→抓flag→submit 必须单链自动化**（shell 管道或单 python 进程），submit 前实例死亡=白打。
- start_challenge 限流 10s/次、submit 3s/次；429 就 sleep 重试。
- **会话作用域先测清楚**（决定打法）：新 cookie 会话 GET 钱包/订单，对比数值——
  - 钱包/券池/订单**全局共享** → 多会话无效，只能竞态或参数绕过；
  - **会话隔离** → 多会话各自是"新用户"，可重复薅（限购类）。
- **卡关合法求助**：`/wp_center?buglabs=<靶场ID>`（WP 编号与靶场 ID 不同空间）、`/sub?id=<wp编号>` 攻略正文、`/SeeImg?guid=<id>` 攻略截图（curl 可直接拉，截图里就是现成 payload）。

## 1. 侦察顺序（固定动作）

1. 首页 HTML 正则提取：`fetch(`/`action=`/`onclick=`/`href=` 端点 + 页面文案（任务目标常写在页面里："让会员超过80天"/"让USDT多起来"）。
2. OPTIONS 探测每个端点的 allowed methods（**DELETE/PUT 变体常是未文档化的隐藏入口**）。
3. `/mine`、`/orders`、`/api/orders`、`/user_center` 类页面必看：订单对象里有 `flag` 字段、`refundable` 字段、`refund_qty` 入参名等关键线索。
4. fuzz 常见隐藏路径：`/api/orders` `/api/wallet` `/api/recharge` `/api/pay` `/mine`。
5. 页面 pattern 残留（如 `data-id="${id}"`）暴露模板变量名。

## 2. 支付类漏洞原语速查（全部实战验证）

### 2.1 客户端价格信任
- `/checkout` body `items:[{product_id,quantity,price}]`、`/buy?product=X&price=Y`：price 服务端不校验 → 0.01 元购旗舰。
- 变体：/buy 负价格 → **余额反向增加**（money = balance - price，price=-1000 → +1000）。

### 2.2 金额符号未校验（负数三类）
- 负数充值：`/pay?prePayMoney=-100` → 余额暴涨。
- 负数购买：同上反向加余额。
- 负数划转：交易所 `amount=-1` → 现货+1/合约-1，**intruder 30 并发循环刷**。

### 2.3 舍入/精度三类
- 四舍五入进位：充 0.001 入账 0.01（round half up）。
- 进一法：充 0.019 入账 0.02（ceil）。
- 截断判定分离：后端按 2 位小数入账但**成功判定用原始值**（充 0.0049 → 显示 0.00 → 访问 /success 直接通关）。
- 上溢：`amount: 1E28`（float 上溢绕过余额校验，spot=-1e28/contract=1e28）。

### 2.4 限购/重复领取绕过
- 领券 `POST /claim/<id>` 无去重 → 第二次领取返回 flag。
- "新人仅限一次"：**未支付订单不计入已购** → 重复 POST /purchase 堆 N 单 → 全部支付 → 会员天数=N×30。
- 串行被封 → Barrier 同步 8~30 线程竞态 POST；仍被封 → raw socket 同步发包；全局状态锁死 → 试多会话（先测作用域）。

### 2.5 退款漏洞三连（最高产，系列题核心）
| 变体 | 原语 | 打法 |
|---|---|---|
| a) 撤销数量 bug | 退 N 张只扣 1 张、退全款 | 循环 买10→退→净赚9张 → 攒到目标券数 → 免单结算 |
| b) 余额入账 TOCTOU | credit 在 status/数量 check 之前 | Barrier 多线程并发同一订单退款，N×全额入账 |
| c) 参数篡改 | `refund_qty` 无 >0 校验 → 负数（券增余额扣）；`refund_amount` 不与订单绑定 → 1 张券退 10 万 | 前端 /mine 页 JS 是参数名权威来源，必读 |
- 通用：先查 `/mine` 页 JS 里的退款 fetch 原始 body（参数名猜不中就白干）。

### 2.6 交易所钱包三连
- 并发划转双花：`POST /api/transfer` 余额校验竞态，5 并发全入账（合约+50/现货-40）。
- amount=-1 反向刷：现货+1/合约-1，并发循环到目标值。
- `amount: 1E28` 上溢：绕过余额校验直接成功（徽章名就叫"上溢"）。

## 3. 经济守恒律分析法（卡关时的数学武器）

当所有 1:1 原语被锁死时，推导守恒恒等式判断可行性：
- 例：`初始券 + Σbought - Σeaten = 券`、`初始余额 + Σcredits - Σspent = 余额`，若每次退款 credit = eaten×10（1:1），则 **券 + 余额/10 = 常数** 恒成立 → 免单需要券≥102 永远不可达（实测封顶 100）。
- **突破口 = 打破守恒的非对称事件**：报错仍入账（check 在 credit 之后）、免单路径跳过余额充足性检查（balance 为负也放行）、负数参数使 deduction 反向。
- 遇到 1:1 封闭系统时，逐个端点问：这个操作有没有"入账但未扣减"或"扣减但未入账"的分支？error 路径的副作用是什么？

## 4. 竞态工程要点

- `threading.Barrier(N)` 同步起跑；不够就 raw socket 自拼 HTTP 报文同发（带 session cookie）。
- 竞态目标排序：余额入账 > 状态翻转 > remaining 扣减 > 库存扣减。
- 区分"全锁死"与"部分锁死"：5 并发全失败=锁；恰好 1 成功=锁；N-1 成功=TOCTOU 可打。
- 多会话并发前先测作用域（§0），全局状态多会话无效。

## 5. 通用经验

- 页面文案即任务书（"超过80天"/"USDT多起来"/"合约拿到意外之财"），先读再做。
- 订单对象字段是攻击面地图：`flag`/`refundable`/`refunded_qty`/`coupons_used` 各自暗示一个漏洞面。
- 响应截断会漏 flag：结算/转账响应**完整打印**再正则搜 flag。
- 数值边界测试集（对一切 amount/qty/price 参数）：`-1` `-100` `0` `0.0001` `1e-5` `1e400` `1E28` `"1e2"`(字符串) `true` `NaN`。**每个端点都过一遍这组**，613/526/941 全是这么打出来的。
- 前端 JS 是参数名与隐藏端点的权威来源（`refund_amount` 这种名字猜是猜不到的）。

## 6. 补充实证原语（第二批）

### 6.1 多参数独立校验组合穿透
- 服务端对 `activity_id` / `amount` / `ord`(商品md5) 三元组**各自独立校验**（amount≤balance、ord∈商品表、id∈商品表），但**不校验三者绑定关系** → A商品的id + B商品的amount + B商品的ord 组合穿透，低价买高价商品。
- 打法：枚举每个参数的合法值域，交叉组合（id用贵的、amount/ord用便宜的）。

### 6.2 出票/履约接口跳过支付校验
- 前端流程：支付 → 响应 `type===0` → 调 `POST /generate_ticket {order_id}` → 订单详情页(含flag)。
- 攻击：跳过支付直接调出票接口；若校验"已支付"，用**负数量下单**(quantity=-1)使订单总额为负，余额校验自然通过 → 支付成功 → 出票 → 详情页 flag。
- 侦察：读前端 JS 的 success 分支，找支付后的"下一步接口"。

### 6.3 订单凭证绕过（traceId/凭证复用）
- 前置下单接口失败（余额不足 code=1），但前端仍会以 `tlogTraceId`（前端随机生成的追踪凭证）调用 `process_payment`。
- **process_payment 不校验前置是否成功** → 直接带凭证调它，flag 直接在支付结果 HTML 里。
- 打法：完整模拟前端两步流程，第二步无视第一步的业务失败。

### 6.4 响应状态字段判定的前端逻辑（response-tamper 面）
- 前端以响应 `data.type === "0"` 判支付成功 → Burp 改响应包让前端走成功分支调用后续接口。
- API 化时等价于：直接调用成功分支的后续接口（6.2），或请求侧 mass-assignment 注入 type（视服务端是否信任）。

## 7. 竞态工程补充（352/354 实证）

### 7.1 持续轰炸 vs 一次性齐发
- **一次性 Barrier 齐发 30 线程可能全败**（服务端锁/时序），但**持续轰炸**（30 线程 × 循环至 700+ 请求）几乎必中 TOCTOU 窗口——每请求进入 handler 的时序自然错开，总有一些落在"检查通过后、写入前"。
- 实证：352 检查"已添加该套餐"被全局锁，8 线程齐发 0 命中；持续轰炸 729 请求 → **30 单全部创建成功**。
- 参数：30 并发线程，stop 条件（成功数≥目标 或 请求数≥700）。

### 7.2 多客户端窗口轮替（354）
- "多客户端"类题：全局"已添加"锁**按窗口轮替放行**——session0 买成功 → session1 被拦 → session2 又成功 → …
- 打法：多 session（新 CookieJar）各自 `GET /` 预热 → POST purchase → 查 /orders → 支付自己会话的单 → 任一 session 查 user_center 拿 flag。
- 失败会话的下一次尝试可能恰好落在放行窗口，循环多试几轮。

### 7.3 SPU/SKU 隐藏商品 IDOR（117）
- 商品列表页空壳无接口 → **HTML 注释与 onclick 跳转暴露 API 路径**（`/ada-steam-mall-api/api/spus/10001`）。
- ID 扫描以**响应长度**分类：1713B="已售罄"专用404、1761B="商品不存在"、**9075B=隐藏商品详情页**（本例 spu 12345，ID 与已展示的 10001/10002 完全不连续——隐藏 ID 的取值要撒大网）。
- 详情页 onclick 暴露下一跳 `/test2?spu_id=12345`（确认订单页）→ 到达即购买（纯前端 alert，平台 has_flag=0 无需提交）。
