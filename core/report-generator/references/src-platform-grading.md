# SRC 平台定级速查与提交语言艺术

> **适用范围：仅国内 SRC/众测**（顺丰/360/平安/CNVD/EDU 体系）。国外 bug bounty（HackerOne/Bugcrowd/YesWeHack）用各自 policy + VRT 定级，**勿套用本表条数规则**；但 §三 的"标题=资产+漏洞+影响、危害三视角、impact 写作"国外同样适用（英文报告同理，impact 优先）。渗透测试/红队报告不使用本文件（走 report-generator §2 主模板）。
>
> 来源：隐雾SRC课件收录的各平台公开规则（顺丰/360/平安等）+ 实战提交经验。**平台规则会更新，提交前以官方规则页为准**；本表用于快速自评定级和写报告时"对表扩写危害"。

## 一、通用定级规律（跨平台）

| 规律 | 说明 |
|------|------|
| 数据量决定档位 | 三要素组合（姓名+电话+证件等）条数直接定级：如某平台 员工三要素≥10万=严重、≥1万=高危、<50条=中危；条数务必写进标题 |
| SSRF 按回显分级 | 全回显取内网敏感信息=高危（禁扫内网）；部分回显=中危；可达无回显=低危；不可达不收 |
| RCE/GetShell=严重 | 上传 WebShell、任意代码执行、SQLi 拖库、缓冲区溢出拿权限 |
| 资金损失看上限 | 可直接提现且影响>10万=严重；积分/羊毛类=高危；绕付费=中危 |
| 越权看对象 | 管理员可读可操作=紧急~高危；普通用户敏感数据=高危；非敏感=中低 |
| 现象≠漏洞 | Self-XSS、无敏感数据 JSON 劫持、401 钓鱼、内网 IP 泄露、无意义源码泄露、swagger 纯泄露（多数平台低危或不收）、无敏感操作 CSRF → 不收或忽略 |

## 二、代表平台要点（节选）

### 顺丰SRC（数据条款细，适合对表估级）
- 严重：直接致系统不可用；批量泄露（员工三要素≥10万/用户≥100万）；资金损失>10万可直接提现；获取核心系统权限；核心账号体系任意登录/改密
- 高危：批量泄露（员工≥1万）；后台弱口令/未授权用管理员功能；积分资产修改/大额羊毛；任意文件读/下载/删；子域名劫持；**全回显 SSRF（须验证可达内网，禁扫描）**
- 中危：普通泄露；交互型（JSON劫持/敏感CSRF/一般存储XSS）；普通越权增删改查；**批量大额券（≤6折且>20张）**；部分回显SSRF；绕付费/试用期延长
- 低危：路径/SVN/phpinfo/URL跳转；撞库爆破；可达无回显SSRF；短信轰炸>20条/分钟
- 忽略：无危害bug、不可利用、非业务资产、测试环境(sit/test/uat/stg)、蜜罐、PDF XSS、不重要并发（阅读量/点赞）、无法利用的API Key泄露
- 特色条款：小程序密钥泄露未证高危利用≤中危；实时批量运单号路由=中危

### 360SRC
- 严重：核心服务器权限 / 严重信息泄露（重要DB注入）/ 核心账密校验逻辑
- 高危：重要业务敏感数据 / 权限绕过 / 文件遍历包含读取 / 绕认证进后台
- PC客户端：远程RCE=严重；主动防御绕过=高危；本地RCE/DLL劫持=中危
- 智能硬件：无条件远程RCE=严重；局域网RCE=高危

### 平安SRC（金融版，收得宽）
- 严重：系统权限类（RCE/WebShell/核心DB注入）；账户支付逻辑（任意登录/改密/资金消费）；核心DB泄露（ID连续可批量三要素+）
- 高危：批量三要素泄露；绕认证操作后台；**可回显访问内网SSRF**；任意文件包含/读/删
- 中危：springboot未授权端点；弱验证爆破（需完整证明）；**无回显内网SSRF**；敏感CSRF
- 低危：URL重定向钓鱼；短信/邮箱轰炸（>30条/分钟需证明）；反射XSS；登录后台不涉敏感
- 特色：**金融行业评级整体上浮一档**（企业低危≈金融中危，300元/个左右）；demo代码含敏感配置也收

## 三、提交语言艺术（写好标题/危害=定级上限）

### 3.1 标题公式
```
xx公司 + xx系统/功能点 + 存在xx漏洞 + 导致xx危害（+ 数据条数）
```
条数进标题直接拉档：
- 低危写法：A系统存在敏感信息泄露漏洞
- 中危写法：A系统存在敏感信息泄露漏洞（5000条）
- 高危写法：xx公司A系统存在敏感信息泄露漏洞导致20001条敏感信息泄露（手机号、身份证）

### 3.2 危害三视角扩写（每个漏洞都过一遍）
1. **对用户**：安全威胁/被售卖/被冒用
2. **对公司/平台**：信誉/舆情/合规（《个保法》处罚）
3. **对业务场景**：该功能被破坏后的连锁反应（如总投递数有收录上限）

模板（泄露类）：
> xx功能点返回包存在敏感信息泄露，遍历id参数可获取全站{n}条记录，包含{字段清单}。用户敏感信息泄露可被不法分子用于{诈骗/撞库/售卖}；对{公司}造成{合规/声誉}影响。

### 3.3 结构（SRC提交单）
```
漏洞标题：三要素公式
漏洞类型：事件型/通用型；APP/WEB/小程序
厂商与资产证明：ICP备案查询截图（beian.miit.gov.cn）/SRC公告收录截图/小程序主体
漏洞等级自评：按 §一/§二 对表
漏洞简述：一句话公式 + 三视角影响
复现步骤：
  1. 资产证明
  2. 系统入口+地址
  3. 步骤1（每步截图，贯穿危害说明）
  4. 步骤2 ...
修复建议：针对性（可写错，平台会纠正，空着不写扣印象）
```

### 3.4 提交策略
- **一洞多交**：不同 URL/不同端（web/h5/小程序/APP）分开交；越权一处得手→同系统逐接口找同类
- **精写对象**：高危严重 + 信息泄露/未授权/越权/业务逻辑四类必精写（回报高）；低危简写
- **先低后高试水**：不确定平台收不收（如短信轰炸/URL跳转），交1个看审核态度
- **6位验证码**：多数 SRC 不收，部分众测/内部项目收中高危——别因刻板印象直接丢
- 报告写不好=白挖：交之前自问"审核员会用哪条理由拒绝"（对应 vuln-hunting Interrogation 门）
