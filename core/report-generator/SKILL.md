# 渗透测试报告生成器

## 核心职责

将测试过程中积累的所有发现自动整理为标准化报告，消除手动整理的重复劳动。

---

## 1. 数据来源（按优先级）

1. **Burp Repeater** — 已命名的VULN{n}条目（`proxy_history`查询带VULN前缀的；**仅 Burp 启用时可用**——Phase 0-A 默认不启用 Burp 时，VULN 条目改为记录在黑板 verified_findings + 阶段 Markdown，见第3条）
2. **会话上下文** — 当前对话中已确认的ConfirmedVulnerability节点
3. **Markdown暂存** — 测试过程中写的阶段性.md文件
4. **Burp Scanner Issues** — `scanner_task_issues` 输出（如跑过scanner）

## 3. 生成规则

### 排序
- 漏洞总览与详情一一对应
- 按严重程度排序：严重→高→中→低
- 同级别内按影响范围排序

### 数据呈现（原生数据，禁止脱敏）
- **报告一律使用原生数据**：响应证据必须为原始响应的逐字引用，PoC 为实际发送的完整报文
- **禁止任何形式的脱敏/打码/截断/占位**：`***`、`[已脱敏]`、`138****5678`、`<省略>` 等一律不允许
- 手机号、身份证、姓名、密码、Cookie、Token、密钥、Base64 等完整原样展示
- 仅在用户明确要求脱敏时才执行脱敏处理

### 漏洞定级标准（人工渗透标准，非扫描器标准）
- **不按漏扫器标准收录**：安全响应头缺失、算法位数偏弱（如 RSA 1024）、平台/组件暴露等扫描器级条目**不进入漏洞清单**
- **信息级一律定低危**：漏洞清单最低档为低危，不使用"信息/Info"档
- 事故类（部署缺陷、可用性故障）、被 WAF/防护有效拦截的疑似点**不算漏洞**，如需提及仅以一句话带入测试说明，不设附录
- 报告结构固定五段：渗透结果 → 漏洞总览 → 漏洞详情 → 安全建议 → 测试资产清理清单（无附录、无测试限制说明）

### PoC完整性
- 每个漏洞必须包含可直接在Burp Repeater中重放的完整请求
- Header完整（从测试时的实际请求复制）
- Body如有必须包含

### 修复建议
- 给出具体代码级修复方向，不说"加强安全防护"之类的废话
- 按漏洞类型给针对性方案

---

## 4. 执行流程

1. **收集** — 从上述数据来源提取所有已确认漏洞
2. **去重** — 同一接口同一漏洞类型合并
3. **排序** — 按严重程度+影响范围
4. **补充** — 检查每个漏洞的PoC/响应证据是否完整，不完整的标注
5. **攻击链** — 分析漏洞间是否存在串联利用路径
6. **生成** — 按模板输出完整报告
7. **写文件** — 保存为 `{目标名}-渗透报告-{日期}.md`

---

## 5. 快捷指令

- `写报告` / `出报告` — 生成完整报告
- `SRC提交单` / `写提交` — 按 §6 生成 SRC 平台提交版（逐漏洞）
- `更新报告` — 在已有报告基础上追加新发现
- `报告摘要` — 只输出渗透结果段（漏洞数+影响+评定）

---

## 6. SRC 平台提交版（给平台审核，≠渗透报告）

用户说"SRC提交/写提交单/交洞"时切换本模式，定级速查与语言艺术详见 `references/src-platform-grading.md`：

- **标题三要素**：`xx公司+xx系统+存在xx漏洞+导致xx危害（+条数）`——条数直接决定档位（5000条 vs 20001条写法不同）
- **危害三视角**：对用户/对公司/对业务场景，逐条扩写；复现步骤里每步贯穿危害
- **资产证明前置**：ICP 备案（beian.miit.gov.cn）/SRC 公告截图/小程序主体，第一项复现步骤就是它
- **对表定级**：按平台规则表自评（references/src-platform-grading.md 有顺丰/360/平安速查）；不确定收不收的先交一个试态度
- **一洞多交**：不同 URL/端（web/h5/小程序）分开成单
- 证据仍按 §3 原生数据规则（平台要完整请求响应，可脱敏的是截图展示而非数据本身——以平台要求为准）
